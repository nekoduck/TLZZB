# ADR-0002：在场与离场两套推演的边界，以及谁推进一个人的打算

**Status:** Accepted
**Date:** 2026-11-15
**Deciders:** 项目所有者；实现方按 `docs/PLAN.md` 第 4.2、5.7、8.1、8.2 节执行

## Context

方案借 S.T.A.L.K.E.R. 的 A-Life，把世界分成两套推演：玩家身边的人完整模拟（每个微轮由模型抉择），远处的人简化模拟（按打算的 `takes` 与 `offscreen` 结算）。两套写的是同一份世界状态（方案 8.2）。

接线时暴露出三个问题，它们都出在「一个人的打算由谁推进」上：

1. **两头都推，或两头都不推。** 内核的 `resolve.apply` 在在场者的动作符合当前这一步时推进游标；`world.tick` 推进离场者。玩家一走一来，同一个人在一个时辰里可能被两边各推一次，也可能两边都不管。
2. **在场的「等」会落后于时间。** 在场的人只有被选为反应者、并且选了「等 1 刻」时，`wait` 类的一步才记进度。玩家一个动作耗 8 刻，他的「看比剑 16 刻」只走了 1 刻，于是玩家在场时世界反而走得慢。
3. **分岔检测做了两份。** `world.baseline` 与 `storyteller.chronicle` 各有一套对照参照点的逻辑，记账的地方也不同，结果可能不一致。

约束：内核不能 import 上层；上层模块之间不能互相 import；所有状态变化只经效果；整局要能重放。

## Decision

1. **边界只有一条：与玩家同处一地即「在场」，其余都是「离场」**（方案 8.1），每次用到时现算，不缓存。
2. **推进打算的职责按边界一分为二，互不越界：**
   - 在场者：动作由 `minds` 抉择、`resolve.apply` 结算；动作符合当前一步的 `do`，内核就地推进这一步。
   - 离场者：只由 `world.offscreen.advance` 推进，每个时辰一次，一个时辰至多动手一次。
   - 在场者的 `wait` 类步骤：时间过去多少就记多少。由 `world.onscene_elapsed(state, defs, ticks)` 在 `game.pass_time` 里补记，经 `progress` 效果写入，记满 `takes` 就算做完。
3. **时间只在一处推进：`game.pass_time`。** 它按时辰边界切块：每块先 `kernel.advance_time`，再补在场者的等待进度；每跨一个时辰调用一次 `world.tick`。`world.tick` 自己不推进时间。长动作（歇息、研读、赶路）中途有动静传到玩家耳目，就在那一刻打断。
4. **分岔只有一个检测者：`world.baseline.check`**，每个时辰由 `world.tick` 调用，经内核的 `diverge` 效果写入 `state.divergences`。`storyteller` 只读这份清单来写年谱和收场时的列表。参照点不参与任何决定事情走向的规则。

## Options Considered

### Option A：按边界分工，时间集中在 game 推进（采用）

| 维度 | 评估 |
| --- | --- |
| 复杂度 | 中：多一个 `onscene_elapsed` 辅助函数，`pass_time` 要切块 |
| 成本 | 低：离场者不调模型（除非一步是开口，要问对方一次） |
| 可扩展性 | 好：地图变大只增加离场者，在场的模型调用量不变 |
| 熟悉度 | 即 A-Life 的在线与离线两套模拟 |

**Pros：** 每个人每个时辰只有一个推进者；玩家在不在场，世界的快慢一致；重放只依赖调用顺序与种子。
**Cons：** 玩家进出一个地点的那一刻，同一个人换了一套推演，行为的细腻程度有落差；路过的中间地点在一个时辰内可能被跳过。

### Option B：所有人都完整模拟

| 维度 | 评估 |
| --- | --- |
| 复杂度 | 低：只有一套推演 |
| 成本 | 高：每个时辰约 25 人各问一次模型，成本与时延翻数倍 |
| 可扩展性 | 差：人数一多就撑不住 |
| 熟悉度 | Generative Agents 的做法 |

**Pros：** 没有边界，行为一致。
**Cons：** 违背时延预算（首字中位数 3 秒）与成本预算（每回合约 1 美分）；基线跑与 2,000 回合试探会慢到不可用。

### Option C：所有人都简化模拟，玩家身边只加叙述

| 维度 | 评估 |
| --- | --- |
| 复杂度 | 低 |
| 成本 | 最低 |
| 可扩展性 | 好 |
| 熟悉度 | 传统的日程表 NPC |

**Pros：** 完全确定，便宜。
**Cons：** 在场的人不会对玩家的言行做出自己的抉择，方案 4.2 的微轮、6.6 的请求裁决都落空。它被保留为模型全挂时的退让。

## Trade-off Analysis

A 的代价是边界上的落差，B 的代价是钱和时间，C 的代价是人物不再「自己拿主意」。方案明确要求在场的人都有反应（4.3），也明确给了时延与成本上限，所以只有 A 同时满足。边界落差用两条办法缩小：离场结算用的是同一张判定表（方案 6.4），所以远处的人同样可能失手；离场的开口照样问对方一次（方案 8.2），只是不写叙述。

把时间推进收在 `game.pass_time` 一处，是为了重放：`world.tick` 若自己推进时间，长动作被打断时两边对「现在几刻」会有分歧。

## Consequences

- **变容易：** 「没有幽灵事件」「没有停摆」可以分别在两套推演上测试；基线跑不放玩家，等于全员离场，直接复用 `world.run_days`。
- **变困难：** 内容作者要给每一步写对 `takes` 与 `offscreen`，否则同一步在场与离场的结果会差得太远；`lean` 的情境动作要写 `pre`，免得做过的一拍一直标 ★。
- **要回头看：** 一个时辰内路过中间地点时可能错过那里的情境；离场赶路不掷追逃；`known_to_player` 目前只看起因事件。
